# 네트워크와 HTTP

## 23. HTTP와 HTTPS의 차이는 무엇인가요?

> 상태: ⬜ 미학습

### 답변

HTTPS는 HTTP 메시지를 TLS 위에서 전송해 통신 상대 인증, 기밀성, 무결성을 제공하는 방식입니다. 연결 과정에서 서버가 인증서를 제시하고 클라이언트는 신뢰 체인과 호스트 이름, 유효 기간을 검증합니다. 비대칭키 방식으로 키 교환과 인증을 수행한 뒤 실제 데이터는 효율적인 대칭키 세션 키로 암호화합니다. HTTPS도 서버 내부의 권한 검증이나 안전한 데이터 보관까지 대신하지는 않으므로 애플리케이션 보안과 별도로 봐야 합니다.

### 핵심 키워드

`TLS` · `handshake` · `인증서` · `기밀성` · `무결성` · `세션 키`

### 꼬리 질문

1. 인증서의 신뢰 체인은 어떻게 검증하나요?
2. 대칭키와 비대칭키를 함께 사용하는 이유는 무엇인가요?
3. TLS 종료 지점 뒤의 구간은 어떻게 보호할 수 있나요?

## 24. HTTP 메서드의 의미와 안전성·멱등성을 설명해 주세요.

> 상태: ⬜ 미학습

### 답변

HTTP 메서드는 요청의 의도를 표현합니다. GET과 HEAD는 서버 상태 변경을 목적으로 하지 않는 안전한 메서드이고, PUT과 DELETE는 같은 요청을 여러 번 수행해도 최종 의도 상태가 같은 멱등 메서드입니다. POST는 보통 멱등하지 않으며 PATCH의 멱등성은 문서 형식과 구현에 따라 달라집니다. 멱등성은 응답이 매번 같다는 뜻이 아니라 재시도 후 서버의 의도된 최종 상태가 같다는 뜻입니다.

### 핵심 키워드

`메서드 의미` · `안전성` · `멱등성` · `PUT` · `PATCH` · `재시도`

### 꼬리 질문

1. PUT과 PATCH는 어떻게 다르게 사용하나요?
2. DELETE 응답 코드가 달라도 멱등하다고 할 수 있나요?
3. GET 요청이 서버 로그를 남기면 안전하지 않은 메서드인가요?

## 25. 멱등성과 멱등키를 설명해 주세요.

> 상태: ⬜ 미학습

### 답변

멱등성은 같은 요청을 여러 번 처리해도 서버의 의도된 최종 상태가 한 번 처리했을 때와 같도록 하는 성질입니다. 결제나 보상처럼 POST 재시도가 중복 결과를 만들 수 있는 작업에는 클라이언트가 멱등키를 보내게 할 수 있습니다. 서버는 사용자·작업 범위와 멱등키를 원자적으로 선점하고, 요청 본문 해시와 처리 결과를 저장해 동일 요청에는 기존 결과를 반환합니다. 동시 요청, 실패 중간 상태, 키 만료와 재사용 범위까지 함께 설계해야 합니다.

### 핵심 키워드

`재시도` · `응답 유실` · `중복 처리` · `멱등키` · `원자적 선점` · `요청 해시`

### 꼬리 질문

1. 멱등키 저장과 비즈니스 처리를 어떻게 원자적으로 묶나요?
2. 같은 키로 다른 요청 본문이 오면 어떻게 처리하나요?
3. 멱등키의 보관 기간은 어떤 기준으로 정하나요?

## 26. 쿠키, 세션, JWT의 차이를 설명해 주세요.

> 상태: ⬜ 미학습

### 답변

쿠키는 브라우저가 값을 저장하고 조건에 맞는 요청에 자동으로 전송하는 수단입니다. 서버 세션은 보통 브라우저 쿠키에는 세션 ID만 두고 인증 상태는 서버 저장소에 보관해 즉시 무효화와 상태 변경이 쉽습니다. JWT는 서명된 클레임을 담아 서버가 별도 조회 없이 검증할 수 있지만 payload가 자동으로 암호화되는 것은 아니며 만료 전 폐기와 키 회전, 탈취 대응이 더 복잡합니다. 브라우저에서는 `Secure`, `HttpOnly`, `SameSite`와 CSRF·XSS 대응을 함께 설계합니다.

### 핵심 키워드

`쿠키` · `세션 ID` · `서버 상태` · `JWT 서명` · `access token` · `refresh token` · `CSRF`

### 꼬리 질문

1. JWT 서명과 암호화는 어떻게 다른가요?
2. JWT 기반 로그아웃은 어떻게 구현할 수 있나요?
3. `SameSite` 속성은 CSRF 위험을 어떻게 줄이나요?

## 27. TCP와 UDP의 차이와 TCP 연결 과정을 설명해 주세요.

> 상태: ⬜ 미학습

### 답변

TCP는 연결 지향 바이트 스트림으로 순서 번호, 수신 확인, 재전송, 흐름 제어와 혼잡 제어를 제공합니다. UDP는 연결 설정 없이 독립된 데이터그램을 보내며 전달·순서·중복 제거를 보장하지 않아 필요한 신뢰성을 애플리케이션이 선택할 수 있습니다. TCP 연결은 클라이언트의 SYN, 서버의 SYN-ACK, 클라이언트의 ACK로 이어지는 3-way handshake를 통해 양방향 통신 가능성과 초기 순서 번호를 확인합니다. TCP는 메시지 경계를 보장하지 않으므로 애플리케이션 프로토콜이 길이나 구분자를 정의해야 합니다.

### 핵심 키워드

`연결 지향` · `바이트 스트림` · `순서 번호` · `재전송` · `흐름 제어` · `혼잡 제어`

### 꼬리 질문

1. 흐름 제어와 혼잡 제어는 어떻게 다른가요?
2. TCP의 한 번의 write와 한 번의 read가 일치하지 않는 이유는 무엇인가요?
3. QUIC은 UDP 위에서 어떻게 신뢰성을 제공하나요?
