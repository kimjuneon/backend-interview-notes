# 프로젝트 기반 질문

아래 답변은 이력서에 적힌 사실만으로 구성했습니다. 면접 전 실제 코드에서 트랜잭션 경계, 재시도 횟수, 캐시 갱신 방식, 이벤트 중복 처리 방식과 개선 수치를 확인해 답변을 보강합니다.

## Ku-ring Backend

### 41. 대량 공지 수집 구조를 왜 페이지 단위로 변경했나요?

> 상태: ⬜ 미학습

#### 답변

기존에는 전체 공지를 한 요청 흐름에서 수집해 대상 데이터가 늘거나 일부 페이지가 실패했을 때 전체 작업의 안정성이 낮아질 수 있었습니다. 이를 페이지 단위 수집과 병합 구조로 바꿔 처리 단위를 작게 만들고, HTML 구조가 다른 경우에는 fallback 파싱을 적용했습니다. 이 선택으로 실패 지점을 더 구체적으로 확인하고 변화하는 공지 페이지 구조에 대응하기 쉬워졌습니다. 면접에서는 변경 전후 처리 건수, 실패율, 수행 시간처럼 실제로 확인 가능한 수치를 추가해 효과를 증명하겠습니다.

#### 꼬리 질문

1. 페이지 일부가 실패했을 때 전체 작업은 어떻게 처리하나요?
2. 페이지 병합 과정의 중복과 순서는 어떻게 보장하나요?
3. 병렬 수집을 적용한다면 동시 요청 수는 어떤 기준으로 제한하나요?

### 42. HTML 구조 변화에 대응하는 fallback 파싱은 어떻게 설계했나요?

> 상태: ⬜ 미학습

#### 답변

공지 제공처의 HTML을 외부 계약으로 보고, 기본 구조를 해석하는 파서와 구조 차이를 흡수하는 fallback 경로를 분리했습니다. 한 선택자에 모든 로직을 묶지 않고 파싱 책임을 좁혀 변경 지점을 제한하는 것이 핵심입니다. 파싱 실패는 정상적인 빈 결과와 구분해 관찰할 수 있어야 하며, 대표 HTML fixture로 기본·fallback·실패 시나리오를 테스트해야 합니다. 실제 면접에서는 적용한 우선순위와 실패 로그 필드를 코드 기준으로 설명하겠습니다.

#### 꼬리 질문

1. fallback이 잘못된 데이터를 정상으로 오인하는 문제는 어떻게 막나요?
2. HTML fixture 테스트는 어떤 경우에 깨져야 하나요?
3. 스크래핑 대상 서버에 부하를 주지 않기 위한 정책은 무엇인가요?

### 43. 알림 메시지 조합을 Assembler로 분리한 이유는 무엇인가요?

> 상태: ⬜ 미학습

#### 답변

이벤트마다 제목·본문·부가 데이터를 조합하는 규칙과 Firebase 전송 코드가 섞이면 메시지 종류가 늘 때 변경 범위가 커집니다. 그래서 이벤트를 공통 `NotificationCommand`로 바꾸는 책임을 Assembler에 두고, 실제 전송은 Adapter가 담당하도록 분리했습니다. 도메인과 애플리케이션 계층은 Firebase SDK를 직접 알지 않아도 되고, 메시지 조합은 순수한 단위 테스트로 검증할 수 있습니다. 전송 채널이 추가되더라도 command 계약을 유지하면서 adapter를 교체하거나 확장할 수 있습니다.

#### 꼬리 질문

1. `NotificationCommand`에는 어떤 정보까지 포함해야 하나요?
2. Assembler가 너무 많은 분기문을 가지면 어떻게 개선하나요?
3. 푸시 전송 실패를 도메인 실패와 어떻게 분리하나요?

### 44. 알림 전송의 retry/recover 정책과 테스트는 어떻게 구성했나요?

> 상태: ⬜ 미학습

#### 답변

외부 알림 시스템의 일시적 실패와 재시도해도 해결되지 않는 실패를 구분하는 것이 먼저입니다. 재시도 가능한 예외에만 retry를 적용하고, 최종 실패는 recover 경로에서 기록하거나 후속 조치 대상으로 남기도록 구성했습니다. 실제 Firebase 호출 없이 실패 순서와 최종 결과를 재현할 수 있도록 fake adapter를 사용했고, 단위·통합·이벤트 리스너·Firebase adapter 테스트로 경계를 나눠 검증했습니다. 정확한 재시도 횟수와 지연 정책은 실제 설정을 확인해 답하겠습니다.

#### 꼬리 질문

1. 재시도하면 안 되는 예외는 어떻게 분류하나요?
2. 같은 알림이 중복 전송될 가능성은 어떻게 다루나요?
3. recover 이후 운영자가 확인할 수 있는 정보는 무엇인가요?

### 45. ArchUnit으로 어떤 아키텍처 규칙을 검증했나요?

> 상태: ⬜ 미학습

#### 답변

Port와 Adapter로 의존성을 분리해도 코드 리뷰만으로는 시간이 지나며 역방향 의존이 들어올 수 있습니다. ArchUnit 테스트를 두어 핵심 계층이 외부 인프라 구현에 직접 의존하지 않고, 정해진 계층 방향을 따르는지 자동으로 확인했습니다. 이 테스트는 기능 결과가 아니라 구조적 계약을 CI에서 지속적으로 지키게 한다는 점에 의미가 있습니다. 면접 전 실제 규칙 클래스와 패키지 경계를 확인해 어떤 위반을 막았는지 구체적인 사례로 답하겠습니다.

#### 꼬리 질문

1. 컴파일만으로 잡을 수 없는 의존성 문제는 무엇인가요?
2. ArchUnit 규칙이 리팩터링을 방해하지 않게 하려면 어떻게 해야 하나요?
3. 패키지 구조와 모듈 분리는 어떤 관계가 있나요?

### 46. 매칭 이후 관계 흐름을 어떤 상태와 API로 설계했나요?

> 상태: ⬜ 미학습

#### 답변

매칭 이후에는 상대 프로필·연애관 조회, 호감과 메시지 요청·응답, 추천·평가, 추가 프로필 결제처럼 서로 다른 행위가 하나의 사용자 관계 흐름을 만듭니다. 각 API를 단순 CRUD로 보지 않고 현재 관계 상태에서 허용되는 명령인지 검증하고, 권한이 있는 당사자만 조회·변경할 수 있도록 설계하는 것이 중요했습니다. 결제나 요청 응답처럼 중복 실행이 문제가 되는 동작은 상태 전이와 멱등성을 함께 봐야 합니다. 실제 상태 값과 금지 전이는 코드 기준으로 표로 정리해 면접에 대비하겠습니다.

#### 꼬리 질문

1. 동시에 수락과 거절 요청이 오면 어떻게 정합성을 지키나요?
2. 관계 상태 전이를 엔티티와 서비스 중 어디에서 검증하나요?
3. 추가 프로필 결제의 중복 요청은 어떻게 방지하나요?

### 47. 파일 저장 책임을 Port와 Adapter로 분리한 이유는 무엇인가요?

> 상태: ⬜ 미학습

#### 답변

비즈니스 로직이 S3나 GCP Cloud Storage SDK를 직접 사용하면 저장소 변경과 테스트가 어려워집니다. 그래서 애플리케이션이 필요한 저장·조회·삭제 계약을 Port로 정의하고 Local, S3, GCS 구현을 Adapter로 분리했습니다. 서비스는 저장 위치가 아니라 계약에 의존하므로 개발 환경에서는 Local, 운영 환경에서는 클라우드 구현을 선택할 수 있고 테스트 대역도 쉽게 주입할 수 있습니다. 예외는 SDK 고유 타입을 그대로 퍼뜨리기보다 애플리케이션이 이해하는 실패로 변환하는 것이 좋습니다.

#### 꼬리 질문

1. 저장 성공 후 DB 트랜잭션이 실패하면 파일 정합성을 어떻게 맞추나요?
2. 파일 URL과 object key 중 무엇을 DB에 저장하나요?
3. 여러 Adapter 중 하나를 런타임에 선택하는 방법은 무엇인가요?

### 48. 관리자 JWT 인증과 권한을 어떻게 설계했나요?

> 상태: ⬜ 미학습

#### 답변

관리자 기능은 사용자 상태, 지갑, 정책, 문의 답변, 푸시 발송처럼 영향 범위가 커서 일반 사용자 인증과 권한 경계를 분명히 해야 합니다. 로그인 시 발급한 JWT의 서명과 만료를 검증하고, 인증 이후에도 각 관리 기능에 필요한 역할과 권한을 확인하도록 구성했습니다. JWT에 권한을 넣더라도 payload는 암호화된 정보가 아니므로 민감 정보는 넣지 않고, 권한 변경이 즉시 반영되어야 하는 요구가 있다면 짧은 만료나 서버 측 확인을 함께 고려합니다. 주요 변경은 감사 로그와 연결해 누가 무엇을 했는지 추적할 수 있게 합니다.

#### 꼬리 질문

1. 관리자 권한이 변경됐을 때 기존 JWT는 어떻게 처리하나요?
2. access token이 탈취됐을 때 대응 방법은 무엇인가요?
3. 인증과 인가 실패의 HTTP 상태 코드는 어떻게 구분하나요?

### 49. 관리자 기능에 감사 로그가 필요한 이유와 기록 기준은 무엇인가요?

> 상태: ⬜ 미학습

#### 답변

지갑, 사용자 상태, 운영 정책처럼 결과를 되돌리거나 원인을 추적해야 하는 변경에는 일반 애플리케이션 로그와 별도의 감사 기록이 필요합니다. 행위자, 대상, 작업 종류, 시간, 요청 식별자와 변경 전후의 핵심 값을 남기되 토큰·비밀번호·개인정보는 그대로 기록하지 않습니다. 감사 로그 기록 실패가 본 작업을 막아야 하는지는 기능 위험도와 컴플라이언스 요구에 따라 결정해야 합니다. 조회 권한과 보존 기간, 위변조 방지까지 포함해 운영 정책으로 관리합니다.

#### 꼬리 질문

1. 감사 로그와 일반 디버그 로그는 어떻게 다른가요?
2. 변경 전후 데이터를 어디까지 저장해야 하나요?
3. 감사 로그 자체의 접근 권한과 위변조를 어떻게 통제하나요?

### 50. 출시 환경을 위해 배포 워크플로와 SQL 로그 정책을 어떻게 보강했나요?

> 상태: ⬜ 미학습

#### 답변

운영에서는 로컬 실행 성공보다 같은 절차로 반복 배포하고 장애 시 변경 지점을 추적할 수 있는지가 중요합니다. GCP 배포 워크플로와 수동 배포 트리거를 구성해 배포 경로를 명시하고, Firebase와 GCS 연동은 별도 테스트로 외부 경계를 확인했습니다. SQL 로그는 개발 편의와 운영 보안·비용이 충돌하므로 운영 환경에서 민감 값이나 과도한 쿼리 로그가 남지 않도록 정책을 분리했습니다. 면접에서는 승인 단계, 롤백 방법, 배포 실패 처리 등 실제 workflow 파일을 기준으로 답하겠습니다.

#### 꼬리 질문

1. 자동 배포와 수동 트리거를 함께 둔 이유는 무엇인가요?
2. 운영 SQL 로그에서 어떤 정보가 민감할 수 있나요?
3. 배포 후 정상 여부를 어떤 지표와 health check로 확인하나요?

### 52. Toss 로그인·IAP·광고·Smart Message 연동을 어떻게 격리했나요?

> 상태: ⬜ 미학습

#### 답변

외부 서비스마다 인증 방식, 응답 모델, 오류 코드와 재시도 조건이 다르므로 핵심 게임 로직에서 SDK와 API 세부사항을 분리했습니다. 애플리케이션이 필요한 계약을 연동 계층으로 정의하고, 각 외부 응답은 내부 모델과 예외로 변환해 상위 계층에 노출했습니다. 이를 통해 테스트에서는 실제 네트워크 대신 대역을 사용하고, 공급자 변경이나 장애 정책 수정의 영향을 줄일 수 있습니다. 호출에는 명시적인 타임아웃을 두고 실패가 핵심 트랜잭션을 오래 점유하지 않도록 경계를 나눠야 합니다.

#### 꼬리 질문

1. 외부 API 타임아웃과 재시도는 어떤 기준으로 정하나요?
2. 외부 응답 모델을 내부 도메인에 그대로 사용하면 어떤 문제가 있나요?
3. 결제 검증 API가 일시적으로 실패하면 사용자 경험을 어떻게 설계하나요?

### 53. 광고 리워드 세션의 중복 보상을 어떻게 방지하나요?

> 상태: ⬜ 미학습

#### 답변

광고 보상은 클라이언트가 완료를 여러 번 전달하거나 응답 유실로 재시도할 수 있으므로 단순 요청 횟수대로 지급하면 안 됩니다. 광고 시청 단위를 식별하는 세션을 만들고, 유효한 세션인지와 이미 보상된 세션인지를 서버에서 확인한 뒤 상태 변경과 보상 지급을 하나의 원자적 흐름으로 처리해야 합니다. 동일 세션 요청에는 기존 처리 결과를 돌려주는 멱등성을 적용할 수 있습니다. 실제 구현의 세션 만료, 유니크 제약, 트랜잭션 경계는 코드를 확인해 구체적으로 답하겠습니다.

#### 꼬리 질문

### 56. 거래 서비스에 Hexagonal Architecture를 적용한 이유는 무엇인가요?

#### 답변

UseCase와 Service가 애플리케이션 흐름을 담당하고, Repository와 메시징 구현은 바깥 Adapter로 두어 핵심 규칙이 프레임워크 세부사항에 직접 의존하지 않게 했습니다. 이 구조는 테스트에서 영속성이나 Kafka 대역을 교체하기 쉽고 외부 구현 변경의 영향을 줄입니다. 다만 계층 수가 늘어나는 비용이 있으므로 단순 기능까지 기계적으로 추상화하지 않고 변경 가능성이 큰 경계에 적용합니다.

#### 꼬리 질문

1. Port는 어떤 기준으로 나누나요?
2. 도메인 모델과 JPA 엔티티를 분리했는지, 그 이유는 무엇인가요?

### 58. 동시 완료 요청의 정합성 문제를 낙관적 락으로 어떻게 완화했나요?

> 상태: ⬜ 미학습

#### 답변

구매자와 판매자의 완료 요청이 거의 동시에 같은 거래를 수정하면 두 요청이 같은 이전 상태를 읽고 한쪽 변경을 덮어쓸 수 있습니다. 엔티티 버전을 이용한 낙관적 락으로 충돌을 감지하고, 충돌한 요청은 최신 상태를 다시 읽어 제한된 횟수만 재시도하도록 구성했습니다. 충돌이 드문 상황에서는 긴 비관적 락보다 동시성을 유지하기 유리합니다. 재시도는 전체 트랜잭션 경계를 새로 시작해야 하며, 횟수 제한과 최종 실패 응답을 명확히 해야 합니다.

2. 충돌이 자주 발생하면 어떤 대안을 선택하나요?

### 59. 이벤트 기반 거래 처리에서 중복과 발행 실패를 어떻게 다뤄야 하나요?

> 상태: ⬜ 미학습

#### 답변

Kafka는 환경과 설정에 따라 재전달이 발생할 수 있으므로 소비자는 같은 이벤트가 다시 와도 거래가 중복 생성되거나 상태가 되돌아가지 않게 설계해야 합니다. 이벤트 ID나 비즈니스 키에 유니크 제약을 두고 이미 처리한 요청은 안전하게 무시하거나 기존 결과를 반환하는 방법이 있습니다. DB 변경과 이벤트 발행 사이의 원자성이 중요하면 outbox 패턴을 검토할 수 있습니다. 이력서에는 Kafka 연결과 상태 전이까지만 적혀 있으므로, 실제 프로젝트가 사용한 중복·발행 보장 방식과 구분해 답하겠습니다.

#### 꼬리 질문

1. Kafka의 at-least-once 전달은 소비자 설계에 어떤 영향을 주나요?
2. outbox 패턴은 어떤 문제를 해결하고 어떤 비용이 있나요?
3. 실패 이벤트를 DLQ로 보낼 기준은 어떻게 정하나요?

### 60. MSA 거래 서비스를 어떻게 배포하고 관찰했나요?

> 상태: ⬜ 미학습

#### 답변

Config Server로 환경별 설정을 분리하고 Docker Compose로 로컬 의존 서비스를 재현했습니다. GitHub Actions에서 빌드·테스트·이미지 생성을 자동화하고 Artifact Registry를 통해 배포 가능한 이미지를 관리했습니다. 분산 환경에서는 한 서비스 로그만으로 전체 요청을 보기 어려워 Zipkin과 Grafana Alloy 기반 추적·수집 구성을 사용했습니다. 운영에서는 correlation ID, 거래 ID, 이벤트 ID를 연결해 지연과 실패 구간을 좁히고, 배포 버전과 함께 비교할 수 있어야 합니다.

#### 꼬리 질문

1. 분산 트레이스의 trace ID는 서비스 사이에 어떻게 전파되나요?
2. Config Server 장애가 서비스 기동에 미치는 영향은 무엇인가요?
3. CI/CD에서 어떤 테스트가 실패하면 배포를 막나요?
